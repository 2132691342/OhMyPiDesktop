# 事件总线（hub）

## 定位

引擎与服务层把事件推给前端的**唯一出口**。它不做业务判断，也不解释事件语义。

三件事：给帧编号、留一段可重放的窗口、把帧非阻塞地分发给每个连接。

为什么它必须存在：流式对话要求「增量到达」是默认形态。引擎吐帧、
服务层转发、前端追加，三方都要对「同一件事的第几片」有同一个说法——
那就是 `seq`。

## 设计

```
Hub
├─ seq     int64           单调递增，前端据此发现跳号
├─ ring    []frame         最近 N 帧的环形窗口，断线重连时补发（应用用 1024 帧）
└─ subs    map[*subscriber]struct{}
```

一帧的形状：

```go
type Event struct {
    Seq    int64           `json:"seq"`
    Event  string          `json:"event"`   // namespace:name
    Data   json.RawMessage `json:"data"`
    SentAt int64           `json:"sent_at"`
}
```

`Data` 是 `json.RawMessage` 而不是 `any`：序列化只做一次，
多连接共享同一个 `[]byte`。否则大帧（一整轮 blocks）的广播成本
会随连接数与帧大小相乘。

## 三条不变量

| 不变量 | 原因 |
|---|---|
| 投递必须 O(1) | 慢消费者丢最旧的帧，绝不阻塞广播——一个卡住的窗口不能拖住引擎读协程 |
| **永不 close 订阅者的 channel** | close 一个可能还有人写的 channel 会 panic，而 panic 在广播路径上等于整个后端退出 |
| 丢帧要记账 | 丢掉的区间记在订阅者上，读协程下次写出前补一条 `chat:gap`，前端据此拉快照对账 |

**为什么永不 close**：`subscriber.ch` 由订阅者自己拥有，退订时只置 `dead` 标志
并关闭 `done`。写方（广播）看到 `dead` 就跳过这个订阅者，
而读方（读协程）同时等 `Done` 与 `Stream`，因此能确定地退出。
close 需要「只有一方能写、另一方不再读」的独占保证，而这里不成立。

**为什么丢帧可以接受**：事件带序号，环形窗口内可以补发，超窗则明确要求前端
拉快照对账。假装补全会让界面带着半截状态继续跑，比明确对账更危险。

## 帧序号与缺口

```
订阅端收到 seq=42，前端 lastSeq=40  → 跳号 → 拉一次快照对账
```

缺口由 `TakeGap` 取出并清空，由读协程合成一条 `chat:gap` 帧发出。
`GapFrame` 用「被丢弃的最后一帧」的序号，前端看到跳号就会去对账。

## 会话维度

`Emit(sessionID, event, data)` 的 `sessionID` 用来让前端丢弃别的会话的事件。
它**不进通道名**：一个窗口只显示一个会话，按通道分会让重放变复杂。

非会话事件（引擎就绪、安装进度）传空串，表示全局通道。

## 取舍

| 取舍 | 代价 | 收益 |
|---|---|---|
| 环形窗口而非无限缓冲 | 长断线（超窗）要拉快照 | 内存恒定 |
| 丢最旧而非阻塞 | 极端负载下界面可能少几帧 | 广播永远不被慢消费者拖住 |
| 序列化一次多连接共享 | 单帧大小受最慢连接影响 | 广播成本不随连接数线性放大 |
